# Перенос данных из Supabase

По текущему решению контент наполняется вручную; перенос Supabase не требуется. Инструкция ниже оставлена для необязательного будущего импорта. Новая база содержит начальный модуль CCPA. SQL в `supabase/migrations` содержит схему, отдельные изменения и часть начальных данных; полноценной копии текущего каталога там нет. Нельзя выполнять эти файлы непосредственно в обычном PostgreSQL: они используют `auth.users`, Supabase RLS, Storage, `pgmq`, `pg_net`, Vault и cron.

`backend/migrations` создаёт переносимую схему с прежними названиями полей и UUID. Заказы, статьи, изображения, настройки Paddle, подавленные адреса и токены отписки поддерживаются импортом. Пользователи Supabase Auth и роли его редактора не переносятся: в исходном frontend нет административного интерфейса, в новой версии CMS не добавлена. При необходимости управления контентом потребуется отдельный защищённый интерфейс; сейчас доступны импорт и SQL через локальный Docker exec.

## Экспорт

Остановить редактирование каталога на время окончательного снимка. Перед финальным переключением временно закрыть оформление новых заказов на старом сайте, дождаться обработки его старой очереди и повторить полный экспорт. REST-пагинация не обеспечивает транзакционный снимок при параллельных изменениях; импорт не удаляет записи, исчезнувшие между экспортами. Для окончательного импорта использовать новую пустую целевую БД или отдельно сверить удаления.

Создать локальный файл `.env.migration.local` (не коммитить) с `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Service key нужен для заказов, черновиков, истории писем и отписок. Публичного ключа для полного переноса недостаточно.

```bash
chmod 600 .env.migration.local
python3 scripts/export-supabase.py \
  --env-file .env.migration.local \
  --output backups/supabase-final.json \
  --media-dir frontend/public/media
```

Скрипт читает таблицы через REST с пагинацией, сохраняет UUID и связи, скачивает публичные файлы Storage этого Supabase-проекта и заменяет их ссылки на `/media/<hash>.<ext>`. Изображения сторонних партнёров остаются на их CDN. Ошибка загрузки прерывает экспорт: не получится молча получить снимок с незагруженными изображениями. Снимок содержит персональные данные и создаётся с правами 0600; хранить защищённо. Каталог `backups/` исключён из Git. Изображения в `frontend/public/media` должны попадать в frontend image; после загрузки пересобрать frontend.

Для предварительного переноса только публичного каталога:

```bash
python3 scripts/export-supabase.py --env-file .env --public-only \
  --output backups/catalog-public.json --media-dir frontend/public/media
```

Эта команда использует прежние `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY`. Она не переносит заказы, черновики, отписки или историю писем. Каждый экспорт требует нового имени файла, существующие снимки не перезаписываются. Если старый Supabase-проект недоступен по DNS, нужны рабочий адрес проекта или ранее сохранённый дамп; скрипт не восстанавливает отсутствующие данные из миграций.

## Импорт

Сначала применить миграции. В development:

```bash
docker compose up -d --wait postgres
docker compose run --rm migrate
docker compose run --rm -T migrate php bin/console app:import - < backups/supabase-final.json
```

В production, после первого `scripts/deploy.sh`, до открытия нового сайта:

```bash
bash scripts/backup.sh
bash scripts/prod.sh run --rm -T migrate php bin/console app:import - < backups/supabase-final.json
bash scripts/prod.sh build frontend
bash scripts/prod.sh up -d --no-build --wait
python3 scripts/smoke.py http://127.0.0.1:8080 --require-content
```

Импорт применяет все таблицы одной транзакцией, делает upsert по `id`, выводит количество записей, откатывается при ошибке типа, неизвестных колонках или нарушенной связи. Он не удаляет существующие строки и не создаёт новую очередь писем для старых заказов. Повторный импорт прежнего снимка может восстановить старые значения полей — не выполнять его поверх новых production-заказов без сверки.

Сверить количество и содержимое категорий, партнёров, расширений, услуг, опубликованных/неопубликованных статей, SEO-страниц, заказов и подавленных email. Проверить картинки, основные URL и цены. Если исходник — `pg_dump`, восстановить его в отдельной временной базе с совместимой Supabase-схемой и экспортировать нужные таблицы в JSON; полный Supabase SQL-дамп нельзя восстанавливать поверх рабочей схемы приложения.

## Письма

Заказ и две записи outbox сохраняются одной транзакцией. Worker проверяет `suppressed_emails`, использует Postmark и пишет результат в `email_send_log`. Неудачные отправки получают задержку 30, 60, 120… секунд, максимум час; после восьми попыток остаются для ручной проверки. Контроль:

```bash
bash scripts/prod.sh exec postgres psql -U pubsetup -d pubsetup \
  -c 'SELECT template_name, attempts, available_at, last_error FROM email_outbox WHERE sent_at IS NULL;'
```

Доставка имеет семантику at least once: при сбое после принятия письма Postmark и до commit возможен повтор. Статический Message-ID помогает трассировке, но не гарантирует дедупликацию у провайдера. Старые Lovable webhook/preview/queue endpoints больше не используются. Бounces/complaints Postmark следует подавлять через Postmark и синхронизировать в `suppressed_emails`; автоматический webhook обработки новых bounce/complaint событий в эту миграцию не входит. Старые токены `/email/unsubscribe?token=...` продолжат работать после импорта.
