# Еженедельное обновление каталога

Расписание: воскресенье, 22:00 `Europe/Warsaw`, с учётом перехода на летнее/зимнее время. Задача выполняется вне HTTP-запросов админки командой `app:catalog:refresh`. Она использует те же парсеры, что импорт и Upload. Поиск новых товаров на сайтах вендоров в этот обход не входит.

## Установка на production

Из каталога проекта после получения нового кода:

```bash
bash scripts/backup.sh
bash scripts/deploy.sh
# Сначала посмотреть план изменений без записи в каталог и скачивания медиа:
bash scripts/catalog-refresh.sh --dry-run
# Один раз установить и включить серверный таймер:
sudo bash scripts/install-catalog-refresh-timer.sh
```

`deploy.sh` применяет миграцию `010_catalog_refresh.sql`. Установщик создаёт `pubsetup-catalog-refresh.service` и `.timer` в `/etc/systemd/system`, включает таймер и показывает следующий запуск. Задача работает от пользователя, вызвавшего `sudo` (либо владельца каталога при запуске от root); у него должен быть доступ к Docker. Существующие `.env.production`, `COMPOSE_PROJECT_NAME`, образы и volume изображений используются через `scripts/prod.sh`. Если используется `PUBSETUP_ENV_FILE`, задайте его абсолютный путь в `Environment=...` для сервиса через `systemctl edit`, затем перезапустите таймер. Содержимое env-файла в unit не копируется.

Повторно устанавливать таймер при каждом деплое не требуется, пока путь проекта и расписание не меняются. Установка таймера в репозитории не активирует production автоматически. Если сервер был выключен в плановое время, `Persistent=true` позволяет выполнить пропущенный запуск после его включения.

Проверка состояния:

```bash
systemctl list-timers pubsetup-catalog-refresh.timer
systemctl status pubsetup-catalog-refresh.service
journalctl -u pubsetup-catalog-refresh.service -n 100 --no-pager
```

## Ручные и пробные запуски

```bash
# Полный обход опубликованных модулей:
bash scripts/catalog-refresh.sh
# Один вендор — UUID из настроек вендора:
bash scripts/catalog-refresh.sh --vendor=UUID
# Проверить предполагаемые изменения без изменения каталога:
bash scripts/catalog-refresh.sh --dry-run
# Повторно скачать медиа, в том числе заменённые по прежнему URL:
bash scripts/catalog-refresh.sh --refresh-media
```

`--dry-run` пишет только журнал запуска. Он читает страницы источников, но не меняет модули, категории, логотипы и кеш медиа. По умолчанию между запросами товарных страниц одного сайта выдерживается минимум 3 секунды; CLI допускает `--delay=0..60` для проверки и настройки. Изображения скачиваются последовательно с прежними лимитами размера и времени.

## Поведение

- В очередь попадают опубликованные модули с непустой `original_url`. Список фиксируется в начале запуска. Новые модули, добавленные позже, попадут в следующий обход.
- Проверяется каждый источник. Обновляются только отличающиеся импортируемые поля: числовое форматирование цены/рейтинга не считается изменением. Affiliate-ссылки, вендор, slug, публикация и счётчики сохраняются. Отдельных ручных версий содержимого нет.
- `updated_at` карточки и даты sitemap не меняются при проверке без изменений. `catalog_source_state.checked_at` хранит время последней успешной проверки отдельно.
- Сохраняется соответствие исходных URL изображений локальным файлам. При повторном обходе доступные локальные файлы используются повторно; новые URL и отсутствующие локальные файлы загружаются. Галерея не заменяется частично скачанной. Логотипы повторно используются также между модулями одного процесса.
- Для модулей, импортированных до миграции, первое обновление один раз формирует кеш соответствий медиа. Если вендор заменяет содержимое изображения по неизменному URL, используйте `--refresh-media`; обычный еженедельный обход такую замену не определяет.
- При временной сетевой ошибке/HTTP 408, 429, 500, 502, 503 или 504 есть одна повторная попытка. HTTP 403/404 повторно не запрашиваются в рамках модуля. После трёх подряд ошибочных модулей одного хоста остальные его модули пропускаются до следующего запуска, другие сайты продолжают обрабатываться.
- Если модуль удалили, скрыли или изменили его источник/вендора во время обхода, он пропускается. Перед записью строка блокируется и настройки проверяются повторно.
- PostgreSQL advisory lock не позволяет запустить два обхода одновременно. После аварийного завершения процесса блокировка освобождается, повторный запуск с теми же `--vendor`, `--dry-run` и `--refresh-media` продолжает незавершённую очередь. Уже зафиксированные результаты не повторяются. Сохранение изменений, кеша и результата модуля выполняется в одной транзакции.
- Сервис повторно запускается после аварии с паузой 5 минут, не более трёх быстрых перезапусков за час. Частичные ошибки отдельных вендоров не вызывают бесконечного перезапуска всего обхода: результат остаётся «Частично успешно».

## Статистика

В админке появился раздел `/admin_panel/refreshes` — «Обновления каталога». Он показывает последние 50 запусков: время и длительность, статус, число проверенных и изменённых модулей, результаты без изменений, ошибки, пропуски и предупреждения. Пробные запуски и выборочные обходы отмечаются отдельно. На странице запуска есть результат каждого модуля, количество попыток, ошибки, предупреждения, изменённые поля и значения до/после.

При отсутствии полного запуска за последний срок появляется предупреждение. Если задача записана как выполняющаяся, но heartbeat старше 15 минут или есть общая ошибка, она отображается как прерванная/без прогресса. Обновить статистику можно кнопкой на странице. Время в журнале показывается по Варшаве; приложение не пытается читать системные права/состояние host systemd из контейнера.

## Проверки

`php tests/catalog-refresh.php` проверяет сравнение полей и повторное использование локальных файлов без сети. С `ADMIN_TEST_DATABASE_URL`, указывающим на отдельную базу с суффиксом `_test` и всеми миграциями, дополнительно проверяются записи под runtime-ролью, пробный запуск, реальные и отсутствующие изменения, повторные попытки, блокировка, восстановление очереди и приостановка проблемного хоста. Настоящие сайты вендоров при этих тестах не обходятся.
