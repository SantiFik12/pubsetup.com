# SEO

SEO формируется сервером Next.js из опубликованных данных Symfony API. Деплой использует `SITE_URL`; в локальном Compose это `http://localhost:8085`. Изменения контента и импорта появляются в метатегах и sitemap без пересборки frontend.

## Метаданные и индексация

У модулей отдельно хранятся `seo_title` и `seo_description`, а также исходные метатеги вендора (`seo_source_title`, `seo_source_description`). Импорт и Upload заполняют их автоматически. Название и описание карточки не заменяются SEO-текстом.

Генератор использует метатеги источника, название и доступные возможности модуля. Из перегруженного title выбирается релевантная основная часть и максимум одно полезное уточнение без повторов. Редакционный предел title — 65 символов. Description собирается законченными предложениями до 160 символов; при слишком длинном исходном тексте используются название и реальные возможности модуля. Это обработка текста по правилам, без внешнего AI API и без выдуманных характеристик. Хороший исходный description может сохраняться без изменений.

Миграция `006_module_seo.sql` добавляет поля. Для старых модулей доступна команда, работающая только с сохранёнными данными, без скачивания страниц и изображений:

```bash
docker compose exec backend php bin/console app:seo:refresh
```

По умолчанию заполняются только пустые поля. `--force` явно перегенерирует заполненные поля. Production deploy после миграций автоматически заполняет недостающие SEO-поля. Исходные метатеги старых модулей появятся после следующего Upload; до этого используются уже сохранённые описания и возможности.

Ручное редактирование SEO модулей в админке отключено. Импорт и Upload генерируют базовые поля из источника автоматически, как и остальное импортируемое содержимое. Для проверенных редакционных карточек сервер применяет отдельные данные из `frontend/src/lib/extension-editorial.ts`, см. ниже.

- У публичных страниц собственные title, description, canonical, Open Graph и Twitter metadata. Description очищается от HTML и сокращается до 160 символов.
- Для категорий и вендоров без описания используется описание с их названием. При импорте описание категории также заполняется в БД, если оно пустое; авторский текст не перезаписывается.
- Карточки модулей используют обложку, статьи — своё изображение. Общая картинка `/social-image` генерируется с существующим логотипом в размере 1200×630.
- Пустые категории, вендоры, SEO-лендинги и пустые списки каталога/услуг/блога получают `noindex, follow`.
- Checkout и compare имеют `noindex, follow`. Админка, API, email и переходы `/go` — `noindex` в HTTP-заголовках; вход в админку также содержит meta robots.
- robots.txt разрешает обход, чтобы поисковый робот мог прочитать `noindex`. Административные страницы защищены авторизацией независимо от robots.txt.
- Несуществующие записи возвращают HTTP 404. Опубликованные страницы открыты для индексации. Это не подтверждает фактическое попадание в поисковый индекс.

## JSON-LD

Разметка включена в серверный HTML:

- Organization и WebSite со стабильными `@id`;
- Product для модулей, с реальным вендором как продавцом и его ценой/адресом предложения;
- Service для услуг; цена по запросу не размечается как бесплатная;
- BlogPosting для статей, включая реальные даты публикации и изменения;
- BreadcrumbList и CollectionPage / ItemList для страниц каталога.

Импортированные рейтинги вендоров не выдаются за собственные отзывы pubsetup.com и не включаются в aggregateRating. Наличие товара, сроки действия цены и другие отсутствующие сведения не выдумываются. JSON сериализуется с экранированием HTML-символов для защиты от вставки `</script>` из импортированного контента.

## Sitemap

`/sitemap.xml` генерируется из опубликованного каталога. Пустые разделы и служебные страницы исключены. `lastmod` берётся из `updated_at` / `created_at` / даты статьи; у разделов учитываются даты входящих материалов. Для статических юридических страниц неизвестная дата не подменяется текущим временем. URL удаляются из дублей.

## Проверки без браузера

```bash
npm --prefix frontend run test:seo
npm --prefix frontend run typecheck
npm --prefix frontend run lint
composer --working-dir=backend qa
# Только локальный запущенный Docker-стек:
docker compose exec -T backend php tests/seo-http.php
```

HTTP-проверка читает только локальный gateway: проверяет метатеги, JSON-LD, sitemap, lastmod, пустые категории, noindex, PNG для соцсетей и HTTP 404. Публичный сайт не проверяется.

## Пагинация Extensions

Страница `/extensions` показывает по 24 карточки; номер хранится в `page`. Поиск, фильтры и сортировка применяются сервером ко всему каталогу до разбиения. Поиск включает полное описание, имя, краткое описание, вендора и теги, даже если модуль не был на текущей странице. При изменении фильтров открывается первая страница. Страницы используют стабильный порядок при равных значениях сортировки, ссылки с сохранёнными фильтрами и номером страницы, а также диапазон результатов. Браузер получает только карточки текущей страницы, все варианты вендоров/категорий и список тегов. Optimistic-состояние сохраняет ввод при обновлении маршрута; отправка поиска отложена на 250 мс после изменения текста, устаревшие изменения отменяются. Фильтрация требует соединения с сервером.

Canonical для второй и последующих страниц содержит `?page=N`. JSON-LD CollectionPage включает только карточки текущей страницы. Поисковые/фильтрованные URL и запросы с некорректным номером страницы получают noindex; пустая выдача не индексируется.

Категории, вендоры, теги и SEO-лендинги также показывают по 24 карточки с серверными ссылками пагинации. Порядок — дата создания по убыванию, при равенстве slug по возрастанию, без изменения исходного массива. Canonical и JSON-LD описывают текущую страницу, вторая и последующие страницы получают собственный title с номером. Пустые подборки и некорректные номера страниц получают noindex. Первая страница остаётся по прежнему URL без `page`; sitemap содержит корневые URL подборок, остальные страницы обнаруживаются по ссылкам пагинации.

## Объём данных страницы и обнаружение статей

CatalogProvider находится на уровне страницы, а не общего layout. Общие Header и Footer не требуют каталога. Через `CatalogPage` статья получает своё полное содержимое и только модули, на которые ссылаются её блоки; для остальных статей передаются сводные данные без содержимого и оглавления. Страница блога получает все сводные данные, без модулей. Карточка модуля получает только свой модуль, его партнёра и категорию, а также услуги установки. Главная получает шесть featured-карточек; списки — карточки своей страницы без полных описаний, галерей, подробных возможностей и SEO-полей. Сохраняются обложка (включая fallback на первое фото галереи), краткий текст, теги, цены, рейтинги и ссылки на документацию. Страницы услуг не получают модули. Полный набор пока остаётся у служебных compare и checkout, которые закрыты от индексации. Юридические страницы не получают каталог.

На главной сервером выводятся шесть последних опубликованных статей и ссылка на полный блог. Порядок — дата публикации по убыванию, при равенстве дата создания, затем slug; редактирование старого материала само по себе не поднимает его в «последние». Под статьёй выводятся до трёх других материалов с общими тегами; большее число общих тегов повышает приоритет, при равенстве используется стабильная сортировка slug. Это дополнительные пути обнаружения, а не гарантия индексирования или роста позиций.

Первый пакет, проверка 25 ноября 2026 на production-сборке Webpack с локальной копией публичного API (1 284 модуля, 10 статей): HTML `/blog` — 42 232 байта, проверенных статей — 90 745 и 98 692 байта, карточки Google Drive Integration — 84 868 байт. До изменений публичный HTML блога и проверенных detail-страниц занимал около 3,7 МБ. Это размеры HTML до сжатия; не измерение Core Web Vitals.

Проверены HTTP-ответы 14 маршрутов, наличие ссылок на все статьи с главной и блога, связанные статьи, canonical и index/follow на detail-страницах, 404 неизвестного URL. Unit-тесты ограниченного каталога проверяют зависимости статьи и карточки, неизменность исходного каталога и выбор связанных материалов. Turbopack в текущей среде не смог создать процесс обработки CSS; сборка `npm --prefix frontend run build -- --webpack` прошла.

В том же пакете Next.js и eslint-config-next обновлены до 16.4.6 после предупреждения сборщика и подтверждения через npm audit. Повторная проверка `npm --prefix frontend audit --omit=dev --json` не обнаружила известных уязвимостей production-зависимостей. Это исправление зависимости, не SEO-фактор и не доказательство причины низких позиций.

Второй пакет, проверка на штатной Docker-сборке `next build` с Turbopack: главная — около 112 КБ вместо 3,78 МБ публичного HTML до изменений, `/extensions` — около 254 КБ вместо 3,89 МБ, первая страница Meetanshi — около 239 КБ (24 карточки из 246). Проверены 27 HTTP-маршрутов с копией публичного каталога и дополнительными тестовыми тегом, лендингом и пустыми подборками. В Chrome проверены поиск по слову только в полном описании вне первой страницы, быстрый ввод без запроса на каждую букву, фильтр вендора, пагинация, история браузера, сравнение между страницами и мобильная ширина. Ошибок выполнения/гидратации не обнаружено. Изображения модулей в локальном API-стенде не обслуживаются; доставка изображений этим прогоном не проверялась.

## Редакционные карточки

`frontend/src/lib/extension-editorial.ts` содержит собственные вводные тексты, title/description и заметки по выбору/настройке для Meetanshi Zoho Inventory Integration, Wyomind Data Feed Manager и MageDelight Extra Fee. Выбор основан на показах и запросах Search Console за 26 октября — 22 ноября 2026. Тексты опираются на ссылки производителей, содержат дату проверки и отдельно сформулированные рекомендации для проверки на staging; практическое тестирование модулей не заявляется. Блок `ExtensionBuyingNotes` рендерится сервером.

Редакционные данные применяются только при совпадении slug и домена производителя (для Wyomind учтён также переход на Syde). Они не изменяют записи БД и не стираются очередным импортом. Цена, рейтинг, совместимость и исходное подробное описание остаются импортируемыми. Title/description и краткий текст подменяются в серверной модели перед формированием HTML и JSON-LD. Для `lastmod` используется более поздняя из даты изменения в БД и фиксированной даты редакционной проверки. При изменении заметок нужно актуализировать `reviewedAt`, а не подставлять дату каждого запроса.

Для публикации достаточно обычной пересборки frontend; миграций БД и ручного импорта контента для этих заметок нет.

## Прямые ссылки и единое поведение импорта

Внутренние ссылки обложки и названия в `ExtensionCard` ведут на канонический `/extension/{slug}`, а не на служебный redirect. Старый счётчик вызывается отдельно в фоне; см. `docs/admin-panel.md`. Это общая логика компонента для всего каталога, включая новые импортированные модули. Изменений данных модулей в БД для этого пакета нет. Существующие `/go/module` ссылки совместимы с прежним backend.

Карточка любого модуля получает обратные ссылки на опубликованные статьи, которые действительно ссылаются на его slug: через блок `extension-card` или поддерживаемую inline-ссылку. Нечёткое совпадение названия не используется, дублей одной статьи нет. Отдельный ручной список для Data Feed Manager заменён этим общим правилом. На странице модуля убирается повторное упоминание Magento 2 в имени перед стандартным суффиксом. `Pubsetup Team` размечается автором Organization, а не вымышленным Person.

`backend/tests/seo-import.php` на отдельной базе `_test` проверяет парсер источника, создание модуля, попадание в CatalogService, стабильность URL при обновлении, повторный импорт без дубля и сохранение счётчика. Переменная `SEO_IMPORT_SNAPSHOT` позволяет сохранить до/после для проверки frontend. Обновления и повторный импорт выполняются штатными методами AdminCatalog, без ручных исправлений записей.

Автогенерация редакционных summary для всего каталога в этот пакет не входит. Возможный следующий пилот должен использовать проверяемые факты и источники, а не выдавать пересказ описания за собственное тестирование.
